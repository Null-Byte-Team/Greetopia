Smart Irrigation — Software Specification

For the developer building the cloud/decision-engine layer. The ESP32 firmware (sensor node + camera node) is already built and flashed; this spec covers everything that runs on the laptop/cloud side.

1. System Context

Two independent ESP32 nodes publish data over WiFi. Nothing downstream talks back to the boards except a single watering command. This spec is the "brain" that sits between them and the user.

Sensor nodeMQTTSoil x3 (surface/mid/root), leaf wetness, temp, humidity — every 10s"ON" command → triggers pump for up to 15s (hardware safety cutoff, non-negotiable)

{id} is the plant's unique ID (e.g. plant01) — must match the PLANT_ID set in both firmware files.

3. Modules to Build

3.1 MQTT listener

Subscribes to all plants/+/+ topics on the broker. Keeps the latest value per plant per metric in memory/DB. Fires the decision engine on every new reading, or on a timer (e.g. every 60s) — developer's choice, timer is simpler to start with.

Suggested Python + paho-mqtt

3.2 Photo receiver

HTTP server exposing POST /upload. Reads X-Plant-Id header, saves the JPEG body to disk (or object storage later) as {plant_id}/{timestamp}.jpg, keeps a pointer to "latest photo per plant."

Suggested Flask, single route, no auth needed for prototype stage

3.3 Weather check

On each decision cycle, call OpenWeatherMap (or similar) for the plant's location. Extract: probability/volume of rain in the next 12-24h. Cache the result for ~1 hour to avoid rate limits — no need to call on every single sensor reading.

3.4 VPD calculation

Standard formula using temp + humidity:

svp = 0.6108 * exp((17.27 * T) / (T + 237.3))   // T in °C, saturation vapor pressure (kPa)
vpd = svp * (1 - humidity / 100)                 // kPa

Output a simple stress band (e.g. low / moderate / high) from VPD thresholds — exact cutoffs are a tuning decision, start with literature-typical ranges for houseplants and adjust from observed data.

3.5 Vision check

Runs only when a new photo arrives (not every cycle). Sends the photo to a vision-capable LLM API with a prompt requesting structured JSON only — not freeform text — e.g.:

{"wilting": bool, "discoloration": bool, "spots_or_pests": bool, "confidence": 0-1, "notes": "short string"}

Store the raw JSON alongside the photo. This output feeds the decision engine as one more signal, never the sole trigger.

3.6 Decision engine

Runs on a fixed interval (e.g. every 10-15 min). Pulls: latest root-zone soil %, surface/mid trend, VPD band, weather forecast, latest vision JSON. Produces a boolean watering decision plus a short reason string (for logging and for the chat layer to reference later). Suggested priority order: safety cutoffs first (never water a flooded sensor reading), then root-zone threshold, then weather override (skip if rain expected), then VPD/vision as secondary flags that can lower the threshold slightly, not override it.

3.7 Command + logging

If watering decided: publish "ON" to plants/{id}/water. Either way, write one row per decision cycle to a database: timestamp, all raw readings, weather snapshot, VPD, vision result, decision, reason.

Suggested SQLite for prototype stage, swappable for Postgres later

3.8 Chat + daily diary

Chat: on a user question, pull recent rows from the log DB for that plant, pass them plus the question to an LLM, answer grounded in that data — not open-ended reasoning.

Diary: once daily (cron/scheduled job), pull the day's rows, prompt the LLM to write a short first-person entry from the plant's "perspective," store it alongside the log.

3.9 "Water saved" counter

Maintain a running comparison: estimate what a fixed-schedule baseline (e.g. water X ml every Y hours regardless of conditions) would have used over the same period, versus actual ml delivered (from watering event duration/flow sensor if added later). Surface the delta on the dashboard.

3.10 Plant Species Knowledge Base

A small database the user populates with the plants they're actually farming — species name, growth stage, and ideal care ranges (moisture, light, temperature). This is the grounding layer the chatbot and decision engine lean on instead of fully trusting the camera's species guess every time. On camera setup, the vision AI suggests a species match against this list; the user confirms. The chatbot answers "does my tomato need more water" by checking this plant's actual profile, not by re-analyzing the latest photo from scratch.

Suggested simple table: plants(plant_id, species, growth_stage, ideal_moisture_min, ideal_moisture_max, light_needs, notes) — editable by the user through the control panel below

3.11 Control Panel (manual override)

A dashboard section where the user can act directly, not just the AI:

  • Manual "Water Now" button, with an optional duration slider — publishes ON or ON:<seconds> to plants/{id}/water (the sensor-node firmware now supports the optional duration, capped at its built-in safety limit).
  • Auto/Manual mode toggle per plant — when set to Manual, the decision engine should skip its automatic watering check for that plant until switched back, so a user's manual choice isn't immediately overridden.
  • Manage plants — add/edit entries in the species knowledge base above (species, stage, care ranges).
  • Every manual action gets logged to the same database as automatic ones, tagged source: manual vs source: auto, so the "water saved" counter and the diary can tell them apart.

4. Suggested Tech Stack

Python end to end keeps this simple: paho-mqtt for MQTT, Flask for the photo receiver and any dashboard API, SQLite for storage, requests for the weather API and vision/LLM calls. All modules can run as one process for the prototype, split into services later if needed.

5. Suggested Build Order

1) MQTT listener + logging → 2) Photo receiver → 3) Weather check → 4) VPD calc → 5) Plant species knowledge base (basic CRUD) → 6) Decision engine (soil + weather + VPD + species profile, vision stubbed) → 7) Vision check, wire into decision engine as a secondary signal → 8) Control panel (manual water button, auto/manual toggle, manage plants) → 9) Chat, grounded in both sensor history and species profile → 10) Diary → 11) Water-saved counter.

6. Firmware Note for This Build

Both firmware files are finished and already support everything above — the developer should receive them alongside this spec, not write new firmware from scratch. Two details the developer needs to know when building against them:

  • The water command topic now accepts ON (default duration) or ON:<seconds> (custom duration, still capped by the board's own safety limit) — this is what the control panel's duration slider should send.
  • PLANT_ID is hardcoded per board in the firmware (e.g. "plant01") and must exactly match the ID used in the species knowledge base and all MQTT/HTTP calls for that plant.
